Vite + React + TS SPA. Single-page app with client-side routing.

## Launch decision & recommended configuration (2026-10-04, FINAL)

- **Decision:** keep the non-blocking dashboard with the in-dashboard Tradovate connect. On first access the dashboard shows a dedicated **first-run welcome/connect screen** (`TradovateWelcome.tsx`) — a **SOFT gate, not a blocking gate**: no dashboard content behind it, but the sidebar/other views stay reachable and "Skip for now" dismisses it for good (persisted server-side in `tradovate_welcome_state`). The login-flow gate is intentionally **NOT** part of the product — do **not** build one, and do **not** add `REQUIRE_TRADOVATE_CONNECTION` or any router guard that blocks `/dashboard`. This supersedes every earlier connect-gate idea, including "Option A: no first-run screen".
- **Recommended launch config (Edge secrets):** `TRADOVATE_ENABLED=false` and `AI_KYC_ENABLED=false` until (1) the live Tradovate demo test passes and (2) the AI-provider / ID-data-protection review is signed off. Leave `WITHDRAWAL_KYC_GATE_ENABLED` **unset** (only the exact string `false` disables; `false` refuses withdrawals rather than bypassing KYC — never set it in normal operation). Leave `TRADOVATE_ALLOWED_ENVIRONMENTS` **unset** for demo-only (see below).
- **Go-live order:** Supabase secrets → `supabase db push` (all 7 pending migrations in filename order, head `20261009000000`) → `supabase functions deploy` → `npm run smoke:functions` (no function returns 404) → merge **PR #47 only** (close #45 and #46) → Vercel redeploy → final test in an incognito window with a fresh account. The exact migration list/order and the smoke command are in `docs/supabase-deploy-order.md`.
- **Production deploy state (verified 2026-10-24, RESOLVED).** The SPA is live on Vercel (`braxelmarkets.vercel.app`) and its bundle points at `ymzdxifedtjwkxkzfwqu.supabase.co`. All 34 Edge Functions are deployed (none return 404) and all 7 pending migrations are applied — `tradovate_account_snapshots`, `tradovate_welcome_state`, `kyc_submissions`, `withdrawal_requests`, `kyc_ai_checks` and the KYC gate RPCs all exist, and `supabase migration list` shows LOCAL == REMOTE through head `20261009000000`. Confirm any future release with `SUPABASE_URL=https://ymzdxifedtjwkxkzfwqu.supabase.co npm run smoke:functions` **and** a table probe: a missing table answers `404`, an existing one with RLS answers `200 []` or `400` (no `id` column), never 404.
- **Three deploy-path bugs fixed on 2026-10-24 — do not regress them:**
  1. `20261009000000_tradovate_dashboard_snapshot.sql` had an invalid `DROP POLICY ... ON ... FOR DELETE ...` (the `CREATE POLICY` line was missing, so `FOR DELETE` was glued onto the `DROP`). `supabase db push` failed at that statement, so **no** migration in the chain ever applied. Every `DROP POLICY IF EXISTS x ON t` must be terminated with `;` and followed by its own `CREATE POLICY x ON t FOR ...`.
  2. `deploy-supabase-functions.yml` called `supabase migration list --linked` **without first running `supabase link`**, so the read always failed, `remote` was empty, and the pre-flight skipped the function deploy on every push (the run logs show `Deploy all Edge Functions => skipped`). It now links the project first (guarded on the DB password so it can never block on an interactive prompt).
  3. The pre-flight then matched the expected version against the **whole** `supabase migration list` output. That table prints a LOCAL column (every migration file in the repo, applied or not) and a REMOTE column (what the database actually applied) — both 14-digit-only. Matching the raw text always hit the LOCAL column, so the gate passed on a database that had applied **nothing** (a false positive: functions were deployed while `tradovate_account_snapshots`/`kyc_submissions`/`tradovate_welcome_state` still 404'd). It now normalises the box-drawing `│` to `|`, takes **field 2 (REMOTE) only**, and requires an exact 14-digit match. `make test-migrations` reproduces the chain, but it cannot catch this class of bug — only the REMOTE-column parse can.
- **Fail-open:** the first-run welcome screen is suppressed — normal dashboard, never a blocking state — whenever the `tradovate-status` call fails (404/500/timeout/network) or the welcome-state table is missing. `src/lib/tradovateWelcome.ts` shows it only for an explicit `welcome.show === true`; the server returns 200 and hides it if the skip read throws.

## Tradovate integration
- Server code lives in `supabase/functions/_shared/tradovate/` (crypto, authService, restService, http, rateLimiter, credentialStore, sync, pnl) and the `supabase/functions/tradovate-*` Edge Functions.
- `make test-tradovate` runs every Deno suite (pnl, rate-limit, auth-rest, sync, dashboard, welcome, log-safety, ownership, e2e-demo, connect-error, account-environment). `make test-tradovate-rls` runs the 2-user RLS test against a real Postgres (needs Docker; see `supabase/functions/_test/rls/`).
- There is NO `tradovate-stream`. Edge Functions cannot hold a WebSocket; the data path is incremental polling on `integrations.last_fill_id` (idempotent), scheduled by `20261004000001_tradovate_sync_schedule.sql`, with Supabase Realtime pushing diffs to the browser.
- The connect flow is IN-DASHBOARD, not a gate: login goes straight to the dashboard. On first access the dashboard's default view renders the `TradovateWelcome.tsx` screen instead of dashboard content (black/gold, primary "Log in on Tradovate" CTA opening `TradovateConnectPanel.tsx`, secondary "Skip for now"). It is a SOFT gate: the sidebar and every other view stay reachable, and skip is persisted per user in `tradovate_welcome_state` via `tradovate-status` (`GET` reports `welcome.show`/`welcome.skipped`; `POST {action:"skip"}` records it). `welcome.show` is true only when the feature is on, unconnected, never-connected and not skipped, so a disconnect (revoked row) never re-shows it, and `TRADOVATE_ENABLED=false` hides it. There is no router guard and NO `REQUIRE_TRADOVATE_CONNECTION` flag — do not reintroduce one. The Tradovate view still has its own empty state (`TradovateTrades.tsx`).
- Credentials are AES-256-GCM envelopes `{ciphertext, iv, auth_tag, key_version}`; the browser never sees them and RLS gives authenticated roles no read on `integration_credentials`. `docs/tradovate-runbook.md` has the key-rotation plan.
- App-level API credentials (`cid`/`sec`) are SERVER SECRETS: `TRADOVATE_APP_CID` / `TRADOVATE_APP_SECRET` (plus optional `TRADOVATE_APP_ID` / `TRADOVATE_APP_VERSION`). `resolveAppCredentials()` in `supabase/functions/_shared/tradovate/appCredentials.ts` sends the client-supplied pair if present, else the server pair. The default UX is username + password only; the panel's cid/sec fields are a collapsed "Advanced options" fallback. NEVER add a `VITE_TRADOVATE_APP_*` client env var.
- **Environment policy is SERVER-SIDE and demo-only by default.** `TRADOVATE_ALLOWED_ENVIRONMENTS` (Edge secret, comma-separated) lists the environments the connect function accepts; unset/empty → `["demo"]`, so **live is disabled by default**. Setting `TRADOVATE_ALLOWED_ENVIRONMENTS=demo,live` re-enables live with no code change. The panel no longer offers a demo/live selector — it always sends `environment:"demo"` — but the server is the boundary: a crafted `environment=live` request is rejected `422 environment_not_allowed` (see `supabase/functions/_shared/tradovate/environment.ts`). This mirrors the payments flag posture.
- **Account selection is server-driven; the user never types an account id.** After login the connect function lists the accounts that belong to the Tradovate login (`/account/list`). Exactly one account auto-completes the connection; several require a choice and the **first ACTIVE** account is preselected (the server returns `preselectAccountId`; the panel shows the list with that one selected and a confirm button). If no account is active → `no_active_account`; if the list is empty → `no_accounts`; if the listing call fails → `accounts_unavailable` (our/provider side, never the user's fault). The chosen id is stored on the integration and `tradovate-sync` scopes `/fill/list` to it (`fillList({ accountId })`), so fills/PnL/commission stay tied to that account. Logic lives in `supabase/functions/_shared/tradovate/accountSelection.ts` (pure, unit-tested).
- **Disabled is not "broken".** `TRADOVATE_ENABLED=false` makes the connect function answer `503 { error: "feature_disabled" }`. The panel maps that to a distinct `not_enabled` state ("not enabled yet"), never "Service unavailable". 404/5xx/timeout/network failures keep the `service_unavailable` message. `src/lib/tradovateConnectError.ts` maps `feature_disabled → not_enabled` and is tested by `tradovate-account-environment-tests.ts` [4].

## Error handling / no black screens
- Every route is wrapped by `src/components/ErrorBoundary.tsx` + `Suspense` (`RouteView` in `App.tsx`), and `src/main.tsx` adds a top-level boundary. A render error or failed lazy-chunk import must never unmount the whole app into an empty black page — it shows the localized recovery screen instead.
- The boundary auto-reloads once (throttled by `braxel-chunk-reload-at` in sessionStorage) when a stale hashed chunk fails after a new deploy.
- Use `<Link to="...">` for in-app navigation. Raw `<a href="/...">` does a full reload and bypasses the router; only use it for external links or the `window.location.reload()` escape hatch.
- Return early with a themed loader (`min-h-screen bg-[#05070A]` + `Loader2`), not a bare empty div, for loading states.

## Payments / Supabase
- Checkout + CheckoutSuccess fail closed when `isSupabaseConfigured()` is false (render `PaymentsDisabledNotice` or "could not verify" state).
- **ONE payments gate.** The frontend reads `src/lib/paymentsFlag.ts` (`isPaymentsEnabled()` = `VITE_PAYMENTS_ENABLED === "true" || VITE_TEST_PAYMENT_MODE === "true"`). Every payment Edge Function reads `supabase/functions/_shared/payments-flag.ts` (`PAYMENTS_ENABLED === "true" || TEST_PAYMENT_MODE === "true"`) and fails closed (503 `payments_disabled`) when off. These two modules MUST stay in sync; `npm run check:payments` enforces it. Never re-introduce a raw `import.meta.env` gate in a page or a per-function `Deno.env` gate.
- Frontend flags are Vite build-time env vars (Vercel) and need a redeploy to change. Server flags are Supabase Edge Function secrets and take effect on the next invocation. The server flag is the security boundary; the frontend flag only decides which UI renders.
- `HOW_TO_ENABLE_PAYMENTS.md` is the operator runbook (TEST/LIVE values + rollback).
- Do not touch Stripe price IDs, webhook signature verification, payment/activation logic, Supabase functions, migrations, or RLS.
- Plan prices live in ONE canonical client table: `src/lib/plans.ts` `PLAN_PRICING` (USD). It MUST mirror the server table `supabase/functions/_shared/plans.ts` `PLANS` (`priceCents` + `managedCapitalUsd`). `npm run check:payments` enforces parity; never hard-code prices in a page again.
- Managed Capital is always charged in **USD**. Local currency is presentation only.
- Active checkout methods: `stripe-checkout` (Stripe-verified via webhook), `wise-checkout` (pending_manual), `crypto-checkout` (on-chain confirm). Browser flows never declare the price.
- Real payout destinations come from ONE server resolver: `supabase/functions/_shared/payment-destinations.ts` (Wise `WISE_*` secrets, crypto `CRYPTO_DESTINATION_*` secrets). TEST mode returns the safe placeholders; LIVE mode with a missing destination fails closed (503 `payment_destination_unconfigured`) and must never fall back to the test placeholder. The destination check runs after auth.
- `card-checkout` and `paypal-checkout` are **hard-disabled** (HTTP 410): they used to activate a paid service from client-supplied values with no payment verification. Do not re-enable them; card payments go through `stripe-checkout`.
- Test mode is server-side only (`TEST_PAYMENT_MODE` env). Never trust an `isTest` flag from the request body.

- The terminal opens for any logged-in user. KYC is **not** required to enter the dashboard.
- The in-dashboard KYC banner (`src/components/KycReminderBanner.tsx`) is **non-blocking** and must never read "required" for an unverified user — its headline uses `dashboard.kyc.optionalTitle` ("…required only for withdrawals"). The old gating copy (`dashboard.kyc.required` = "Verification Required") must not be rendered anywhere that blocks the terminal.
- The prominent Tradovate card (`src/components/TradovateConnectCard.tsx`, CTA `tradovate.connectCta` = "Log in on Tradovate" in all 11 locales) is the **first** element in the dashboard services view, above the KYC banner.
- Headless proof of the above: `node scripts/screenshot-dashboard.mjs` (needs `puppeteer-core` + `/usr/bin/chromium`; serves a build and mocks a KYC-less user). Output in `docs/assets/`. Vercel *preview* URLs are behind deployment protection (`<title>Login – Vercel</title>`) and cannot be built/screenshotted without a Vercel token; the branch build must be served locally instead.
- KYC is enforced only when a withdrawal is requested. `src/pages/Dashboard.tsx` (withdraw view) renders `src/components/WithdrawalKycGate.tsx` unless the latest `kyc_submissions.status` is `approved`.
- Documents are uploaded through the authenticated `kyc-submit` Edge Function into the **private** bucket `kyc-documents` at `<user_id>/<uuid>.<ext>`; only object paths are stored, never public URLs. Object RLS keys on `(storage.foldername(name))[1] = auth.uid()::text`.
- `withdrawal-request` is the server-side gate: it reads KYC status via the `kyc_status_for_user(uuid)` SECURITY DEFINER RPC for the **JWT** user and returns 403 `kyc_required` unless approved. A `kycStatus`/`userId` in the request body is ignored.
- `kyc-action` mirrors an owner approve/deny onto the latest submission, records the rejection reason, and emails the user via `_shared/userEmail.ts`.
- `_shared/userEmail.ts` is the single module for **customer-facing** transactional email (analogous to `_shared/email.ts` for owner notifications); do not call `api.resend.com` directly. `npm run check:payments` enforces both.
- AI consistency check at submission (`_shared/kyc/aiDecision.ts`, `aiProvider.ts`, `aiKyc.ts`): advisory, **fails closed** — no key / provider error / malformed / low-confidence / failed check -> manual review; only a clean high-confidence pass auto-approves. Decisions are audited in `kyc_ai_checks` (service-role only). Provider is swappable via `AI_PROVIDER_REGISTRY` + `KYC_AI_PROVIDER` (default `gemini`); `KYC_AI_API_KEY` unset = 100% human review.
- `KYC_MANUAL_REVIEW_THRESHOLD_CENTS` (Edge secret) forces human review for an approved withdrawal at/above that amount (`status=manual_review`).
- Schema: `supabase/migrations/*_kyc_on_withdrawal.sql` (`kyc_submissions`, `withdrawal_requests`, gate RPCs, bucket), `*_ai_kyc_checks.sql` (`kyc_ai_checks`), `*_withdrawal_manual_review.sql` (status + `manual_review` column). Gate RPCs are `service_role`-only.
- Tests: `deno run -A supabase/functions/_test/kyc-gate-tests.ts`, `kyc-document-tests.ts`, `ai-kyc-tests.ts`; RLS/storage isolation `bash supabase/functions/_test/rls-kyc/run.sh` (needs Docker).

## Tradovate integration — audit invariants (2026-10-04)
- **One payments gate, one connect flow.** The terminal opens for any logged-in user; the Tradovate connect card lives in the dashboard (no login gate, no `REQUIRE_TRADOVATE_CONNECTION`). `tradovate-dashboard-tests.ts` pins this.
- **Sync is polling, never a WebSocket.** Edge Functions have a hard wall-clock limit, so there is no `tradovate-stream`. `tradovate-sync` polls `/fill/list` on a `last_fill_id` cursor (pg_cron every 2 min, or an external scheduler). Realtime pushes diffs to the browser.
- **A provider failure must never abort the fan-out batch.** `syncIntegration` classifies and returns `status=error` (it must not throw); both loops in `tradovate-sync/index.ts` also guard per integration. Regression: `tradovate-sync-tests.ts` [3].
- **Real error shapes (probed live against `demo.tradovateapi.com`):** a bad login is **HTTP 200** + `{"errorText":"Incorrect username or password..."}`, not 401; unauthenticated `/account/list` and `/fill/list` return **404**. `authenticate()` classifies the 200-body. Do not assume 4xx.
- **Redact before storing/returning.** `extractErrorText()` runs provider text through `redact()`; `last_error_message` and API responses must never carry a token/password/cid/sec (a proxy can echo the `Authorization` header).
- **RLS:** `integrations`/`tradovate_fills`/`trades` are owner-read-only; `integration_credentials` has **no** authenticated policy (service-role only). Real 2-user test: `bash supabase/functions/_test/rls/run.sh` (needs Docker).
- **Ownership is server-side.** Handlers derive the user from the JWT (`requireUser`); a `user_id` in the body is ignored, and every service-role query is explicitly scoped by `user_id`.
- **Environment is server-side and demo-only by default (2026-10-04).** `TRADOVATE_ALLOWED_ENVIRONMENTS` gates the connect function; unset → demo-only, so `environment=live` is rejected 422 even from a crafted request. The panel has no selector and always sends demo. See `supabase/functions/_shared/tradovate/environment.ts` and `tradovate-account-environment-tests.ts`.
- **Accounts are auto-selected; the user never types an id (2026-10-04).** One account auto-completes; several preselect the first ACTIVE one and require confirmation; the chosen id scopes fills/PnL/commission in `tradovate-sync`. See `supabase/functions/_shared/tradovate/accountSelection.ts`.
- Rotation of `TRADOVATE_ENCRYPTION_KEY` is a re-wrap (`key_version` column exists); see `docs/tradovate-runbook.md`.

## Runtime feature switches (2026-10-04)
- **One module:** `supabase/functions/_shared/features.ts`. Switches are read from Edge Function secrets on every invocation, default **ON**, and only the exact string `"false"` turns a feature off — no redeploy needed to flip. `feature-flag-tests.ts` pins the logic and asserts the wiring in each function.
  - `TRADOVATE_ENABLED=false` → `tradovate-connect`/`tradovate-data` return 503 `feature_disabled`; `tradovate-status` returns `enabled:false` so the card hides (no redeploy); `tradovate-sync` is a no-op.
  - `AI_KYC_ENABLED=false` → `kyc-submit` builds no provider, so every submission falls to human manual review (fails closed).
  - `WITHDRAWAL_KYC_GATE_ENABLED=false` → `withdrawal-request` returns 503. It **refuses** withdrawals rather than allowing KYC-less ones; the gate is never silently bypassed.
- Add a new kill switch to `features.ts` and its `FeatureEnv`, then assert the wiring in `feature-flag-tests.ts`.

## Migrations & function deploy order (2026-10-04)
- Pending migrations (this PR, filename order): `20261004000000_tradovate_integration`, `20261004000001_tradovate_sync_schedule`, `20261005000000_kyc_on_withdrawal`, `20261006000000_ai_kyc_checks`, `20261007000000_withdrawal_manual_review`.
- **Migrations before code.** `deploy-supabase-functions.yml` now has a pre-flight that compares the commit's migration head against the linked DB (`supabase migration list --linked`) and **skips** (fail-safe) the function deploy when migrations are not applied. Needs `SUPABASE_DB_PASSWORD`; without it the deploy is skipped. Runbook: `docs/supabase-deploy-order.md`.
- **The migration chain is NOT self-contained from an empty DB.** `public.services` / `public.profiles` are pre-existing production tables not created by any tracked migration. The LIVE `public.services` shape is `(id, user_id, plan_name, account_id, status, balance, created_at)` — it has **no `plan_id`**, so the payment migrations must `ADD COLUMN IF NOT EXISTS plan_id` before any index keyed on it (this was the `supabase-release` failure: `column "plan_id" does not exist` while creating `services_user_plan_activated_unique`). The LIVE `public.profiles` shape is `(id, created_at)` — it has **no `kyc_status`**, so `20261005000000_kyc_on_withdrawal.sql` must `ADD COLUMN IF NOT EXISTS kyc_status text` before the gate RPCs (`kyc_require_approved`/`kyc_status_for_user`) read the profile fallback (this was the follow-up `supabase-release` failure: `column p.kyc_status does not exist` at statement 5 of that migration). Both are additive and non-destructive. The live `payments`/`pending_payments`/`applications`/`payment_audit_log` tables also exist out-of-band (no tracked migration creates them) and are all empty. `make test-migrations` (`supabase/functions/_test/migrations/apply-order.sh`) reproduces this production baseline (`00_legacy_production_baseline.sql`) and applies every migration in filename order, then re-applies them to prove idempotency. Needs `sudo docker` (`supabase/postgres:15.8.1.085`); the image superuser is `supabase_admin` / password `postgres`, db `postgres`.
- **Keep migrations idempotent and production-shape-faithful.** The legacy chain (payment_foundation / option_a / test_payment_mode / create_applications) is being applied to production for the first time and must tolerate the pre-existing tables and the legacy `services` shape: every `CREATE INDEX`/`CREATE CONSTRAINT` needs `IF NOT EXISTS` or a guard, `read_payment_status(text)` must be `DROP`ped before `CREATE OR REPLACE` (its OUT row type changed between migrations), and columns must be widened only after dropping policies that reference them. When a migration test fails, fix the baseline to match live before trusting a green run.

Deleted: `TradovateTrades`, `ProfitCalculator`, `LiveSignals`, `RiskTransparency`, `PerformanceChart`.
- **Dashboard view-models are pure resolvers** in `src/lib/dashboardData.ts` (`resolvePerformanceSummary` / `resolveTransactions` / `resolveAuditLog`); a user with no closed trades gets `hasData:false` and an explicit empty state, never a fabricated number.
- **Edge-function data path for the terminal:** `tradovate-dashboard` (live balance/positions/orders, server-side snapshot cache with `TRADOVATE_SNAPSHOT_TTL_SECONDS`, `?fresh=1` forces a live read) and `tradovate-data` (reconstructed trades + server-computed performance). Both derive the user from the JWT and ignore any body/query user id.
- **Session-token caching (2026-10-04):** the Tradovate access token is stored **inside the encrypted credential envelope** (`TradovateCredentials.accessToken` / `accessTokenExpiresAt`) and reused while valid via `ensureToken({ stored })`; `storeSessionToken()` persists a fresh one after each auth. This cuts repeated "novel" `/auth/accesstokenrequest` calls (the ones that trigger `p-ticket`/`p-captcha` penalties) on every poll/sync. The token is server-only and never returned to the browser.
- **Rate-limit handling is already in `http.ts`/`rateLimiter.ts`/`authService.ts`:** plain 429 → exponential backoff; `p-time`/`p-ticket` → wait then resend the identical body with `p-ticket`; `p-captcha` → ~1h `CircuitOpenError` (`circuit_open`). UI codes: `rate_limited`, `circuit_open` (see `connectTradovate.errors.*` and `src/lib/tradovateConnectError.ts`).
- **i18n plurals:** count keys must carry real CLDR categories per locale — `terminal.calendarTrades_{one,few,many,other}` and `application.note_limit_*`. `scripts/check-i18n.mjs` validates each locale's plural family (exact categories, only `{{count}}` allowed) and the flat key diff. Never add a count key without its categories in all 11 locales.
- **RTL:** use logical utilities (`ms/me/ps/pe`, `start/end`, `text-start/end`) — physical `ml/mr/pl/pr/left/right` break ar/he. `scripts/check-no-hardcoded-text.mjs` (`npm run check:no-hardcoded`) fails on hardcoded JSX text and `title/placeholder/aria-label/alt` literals in the dashboard surface.
- **Realtime + fallback poll:** `useTradovateTerminal` subscribes to Realtime on `trades`/`tradovate_fills` and also polls the server cache every `VITE_TERMINAL_POLL_MS` (default 30000; `0` disables). The poll never calls Tradovate directly.

## Account activation flow (2026-10-24, `feat/account-activation-flow`) — REPLACES the Tradovate connect model
- **New model, no Tradovate API.** The customer buys an evaluation/funded account **directly from the prop firm** (Tradeify or Lucid) through **our affiliate link**, returns to the panel, **requests activation**, and an operator **approves manually**. The signals plan is a fixed monthly fee. The customer executes the signals **themselves**, in their own account, with a third-party tool. **Braxel never operates the customer's account and never stores broker credentials.** There is no order/copy-trading engine and no `tradovate-*` change in this flow — do not add one.
- **One config module, server-driven.** `supabase/functions/_shared/activation/config.ts` reads `ACTIVATION_FLOW_ENABLED`, `AFFILIATE_TRADEIFY_URL`, `AFFILIATE_LUCID_URL`, `SIGNALS_PLAN_NAME`, `SIGNALS_PLAN_PRICE_CENTS`, `SIGNALS_PLAN_CURRENCY` from Edge secrets. **A firm with no configured affiliate URL is dropped everywhere** (no card, no select option) and the server rejects a submission for it (`firm_not_configured`). Nothing is hard-coded; `npm run check:activation` enforces it. `src/lib/activationConfig.ts` reads the **public** `activation-config` Edge Function (`verify_jwt=false` — public marketing data only, no secret/credential/user data) as the single client source of truth.
- **Kill switch.** `ACTIVATION_FLOW_ENABLED=false` → `activation-submit`/`activation-review` answer `503 feature_disabled`, the `/accounts` cards and the dashboard view disappear, no redeploy. Same `features.ts` posture as `TRADOVATE_ENABLED` (only the exact string `false` turns it off).
- **Public page `/accounts`** (`src/pages/Accounts.tsx`): one card per configured firm; the CTA is a real `<a target="_blank" rel="sponsored noopener noreferrer">`. A visible affiliate-commission disclosure, a 3-step explainer, and a **draft** risk notice. No return/profit/"low risk" promise.
- **Dashboard view "Activate account"** (`src/components/ActivateAccountView.tsx`): firm, plan name, account login (**NO password**), purchase email, a receipt upload (image/PDF, ≤10 MB, type + size validated **server-side** too), notes, and **four mandatory confirmations** (ownership, responsibility, firm rules allow automation, risk read). Shows pending / in review / needs info / approved / rejected with the operator note. When approved it renders `PlanActiveChecklist.tsx` ("Plan active" + a 3-step onboarding whose tool instructions are **placeholders** in `planActive.tools.*`).
- **Schema** `supabase/migrations/20261010000000_account_activation.sql` (idempotent, head after `20261009000000`): `public.account_activations` with RLS — owner SELECT only, **operator SELECT all**, explicit deny for client INSERT/UPDATE/DELETE (writes go through the JWT-verified Edge Functions, exactly like `kyc_submissions`). The operator policy requires a **strict JSON boolean** `app_metadata.operator === true` (mirrors `isOperatorMeta`), unlike the payments policy which casts `::boolean` and would accept the string `"true"`. A **private** bucket `activation-receipts` (path `<user_id>/<uuid>.<ext>`, owner-only object policies); operators read receipts through a **300 s signed URL** minted by `activation-review` — never a public URL.
- **Edge Functions:** `activation-config` (public), `activation-submit` (JWT; validates server-side, rate-limits per ip+user, uploads the receipt, inserts `pending`, notifies the owner via `_shared/email.ts`, fire-and-forget), `activation-review` (JWT **operator-only** via `requireOperator`, uses the shared state machine in `_shared/activation/status.ts`, refuses an illegal transition with `409 invalid_transition`, appends to `payment_audit_log`, emails the customer via `_shared/userEmail.ts`). Nothing calls Tradovate.
- **Operator panel** `/operator/activations` (`src/pages/OperatorActivations.tsx`): filters by firm and status, detail modal, receipt via the signed URL, and approve / reject / request-info / start-review buttons.

Runbook: `docs/account-activation-runbook.md`.

## Activation flow extension — TradersPost onboarding + pilot capacity (2026-10-24, `feat/traderspost-onboarding`) — STACKED on `feat/signals-subscription`
- **TradersPost is the execution tool, run by the CUSTOMER.** `TRADERSPOST_STRATEGY_SHARE_URL` (Edge secret) is the share link for **our** strategy; the customer subscribes to it in **their own** TradersPost account and TradersPost copies signals into the customer's account. Braxel still never operates the account and stores no broker credential. When the secret is unset, `activation-config` returns `tradersPost.shareUrl: null` and the onboarding shows the steps with no subscribe button (fail-closed, no hard-coded URL).
- **Strategy confirmation is a self-declaration, not a payment and not a credential.** `activation-strategy-confirm` (JWT) stamps `strategy_confirmed_at`/`_by` on the customer's **own APPROVED** activation only, is **idempotent** (keeps the first timestamp), and appends to `payment_audit_log` with source `'activation'`. It never calls Tradovate and never reads a body user id. `src/lib/strategyConfirm.ts` is the browser helper.
- **Pilot capacity / waitlist.** `ACTIVATION_MAX_ACTIVE` (Edge secret; unset or `0` = unlimited) caps the number of **approved** activations. `activation-submit` returns `409 { error: "waitlist" }` when full (fail-soft: a count error is never a waitlist); `activation-config` reports `waitlist.enabled` and the dashboard shows the waitlist instead of the form. A customer with an **open** request still sees their status, so an in-flight request is never hidden by a capacity change.
- **Migration** `20261012000000_traderspost_onboarding.sql` (additive, idempotent, after `20261011000000`): two nullable columns on `account_activations` + widens the `payment_audit_log.source` CHECK (whichever variant exists) to allow `'activation'`. Row-scoped RLS already covers the new columns; **no credential column** exists. `make test-migrations` covers it.
- **Operator visibility.** `OperatorActivations.tsx` selects and shows `strategy_confirmed_at` in the request detail.
- **Tests:** `deno run -A supabase/functions/_test/traderspost-onboarding-tests.ts` (JWT scoping, APPROVED-only, idempotency, service-role write, append-only audit, kill switch 503, per-ip/user rate limit, no credential read, no Tradovate call); `npm run check:activation` section `[11]`; the headless flow `node scripts/screenshot-activation-flow.mjs` sections `[5]` (strategy confirm) and `[6]` (waitlist).
